### Particularités du routage Linky

La formule courante -06 est incrémentale ; les paragraphes datés -02 à -05 d'[AUTOMATE_RULEENGINE.md](AUTOMATE_RULEENGINE.md) décrivent des étapes précédentes. Le terme proportionnel complet et l'intégrale cumulée ne sont plus réappliqués sur chaque paquet d'un plateau de mesure.

`LINKY_HOLD_10S` ne permet ni hausse ni intégration sans lecture valide ; maintien seulement après mesure antérieure et pendant moins de 10 s depuis celle-ci. Les gardes production, source, mode OFF et sécurité restent applicables. SafetyManager peut couper avant 10 s.

Les données TIC `PAPP`/`SINSTS`/`SINSTI` sont des puissances apparentes utilisées comme estimation réseau. Une cible logicielle en W ne prouve pas une puissance active exacte. Les modèles en puissance moyenne ne reproduisent pas la métrologie ni les impulsions SSR.

## Défauts et critères de réception

### A — Sorties et autorité des commandes (P1)

Sources : `ActuatorManager::{allOff,syncChannelFromConfig,setCommandPercent}`, `WebUi::saveConfig`, `AutomateManager::{arbitrate,applyFinalCommand}`, `EspNowManager::{handleReceive,acceptActuatorCommand}`.

Couper les anciens GPIO, interruptions et timers avant réaffectation. `allOff()` parcourt la configuration courante et ne retrouve pas une broche disparue. Définir la priorité système OFF avant toute commande non nulle ; ne pas confondre avec OFF manuel d'un actionneur, désormais maintenu.

Bloquer les commandes distantes simulées non nulles. L'envoi radio de zéro ne garantit ni sa réception ni son acceptation avec le TTL actuel. La propriété/durée d'une commande radio doit être arbitrée avec les commandes locales ; le manuel Web ne résout pas ce chemin.

Tests sur banc : sortie ON puis simulation ; modification/suppression GPIO ; OFF avec règle vraie ; NODE_ACTUATOR commandé à distance avec boucle locale active. Vérifier tous les actionneurs, pas seulement SSR1.

### B — Configuration et recovery (P1)

Sources : `RouteurSolaireESP32.ino::setup`, `ConfigManager::{backupConfigToNvs,replaceFile,saveDoc,restoreConfigFromNvs}`, recovery `/upload-fs`.

`LittleFS.begin(true)` autorise le formatage après échec de montage. L'upload efface LittleFS entier. Le backup NVS exige un Wi-Fi configuré, n'est rafraîchi par `saveDoc()` que pour `system.json` et efface l'ancienne copie par `prefs.clear()` avant réécriture. Le passage recovery ne synchronise que les identifiants Wi-Fi. La restauration n'est pas un contrôle d'intégrité indépendant des cinq fichiers.

Autre point confirmé : `replaceFile()` remplace le document en RAM avant `saveDoc()`. En cas d'échec disque, configuration active et persistante peuvent diverger. `saveDoc()` ouvre en `"w"` et ne vérifie pas une taille attendue complète après sérialisation. Prévoir validation, temporaire, relecture, remplacement et commit RAM après succès.

La factory n'authentifie pas les routes de modification ; la validation finale LittleFS ne reconnaît pas une image compatible. Protection de l'interface, sauvegarde complète vérifiée et politique d'échec doivent précéder l'effacement.

Tests : modifier uniquement une règle avant update ; installation sans Wi-Fi ; NVS presque pleine ; coupure d'écriture ; image vide/tronquée/arbitraire ; fichier individuel absent ; reboot. Comparer les cinq JSON avant/après.

### C — Radio et redondance (P1)

Sources : `EspNowManager::{sendMessage,acceptActuatorCommand,handleReceive}`, `RedundancyManager::{checkMasterTimeout,detectSplitBrain}`.

Le TTL compare deux uptimes. Les BACKUP passifs émettent des heartbeats traités comme preuve de vie MASTER ; la réception ne passe pas par `onHeartbeatReceived()`. Son état split brain peut être remplacé par le gestionnaire. Un BACKUP avec `lastMasterHeartbeatMs == 0` ne reprend pas.

Callbacks, chaînes, logs et états partagés restent synchronisés directement par le code radio. La correction ciblée de présence n'est pas une protection générale contre les courses ; une file bornée vers la boucle reste à étudier. `isNodeOk()` et plusieurs rendus d'âge conservent `now >= lastSeenMs` : tester le rebouclage au-delà du seul contrôle de perte.

`MSG_SENSOR_VALUE`/certains `MSG_STATUS` écrivent encore directement dans RuntimeState. Les aligner sur SensorManager avec compatibilité historique et import manuel.

Tests : boots décalés, MASTER + deux BACKUP, double MASTER, BACKUP isolé, retour de l'ancien MASTER, perte radio, horloge rebouclée, ancien epoch et commande retardée/rejouée.

### D — Réactivité et rôles (P1/P2)

Sources : boucle principale, `SafetyManager::{softwareWatchdog,configError}`, `SolarWiFiManager::testConnection`, `MqttManager::connect`, `RuntimeState::roleFromString`, validation GPIO Web.

Timestamp watchdog actualisé juste avant test ; test Wi-Fi bloquant jusqu'à dix secondes ; reconnexion MQTT synchrone. Les métriques ne garantissent pas une coupure pendant un blocage. Prévoir traitements bornés et supervision indépendante adaptée à la plate-forme.

`STANDALONE` n'est pas un `DeviceRole` distinct ; rôle inconnu ramené à MASTER. Les champs fonction/redondance exposés ne séparent pas complètement le comportement. `configError()` exige encore `ssr1_water_heater` et `ssr2_aux`, même pour un nœud spécialisé : valider la sécurité selon capacités/rôle.

La plage GPIO n'assure ni capacité de sortie ni absence de conflit UART/flash/OLED/OneWire. Tester configurations refusées et changements de rôle à chaud, sans activation MASTER implicite.

### E — Règles, persistance et unités (P2)

Sources : `RuleEngine::{evaluateDecision,actionToDecision,timeWindowMatches}`, `ActuatorManager::setMode`, `AutomateManager::{arbitrate,ruleCommand}`.

- Une seule décision de commande est retenue ; pas d'application de toutes les actions affichées.
- `setPowerWatts` traverse une borne 0..100. 500 W sur 1500 W doit donner environ 33,3 %, pas 100 W.
- `setMode` sauvegarde à chaque évaluation, même sans changement : potentiellement quatre écritures/s. Séparer mode runtime et persistance.
- L'éditeur Web existe : « pas d'éditeur WebUI » dans l'ancienne V1 est obsolète. Groupes imbriqués, variables utilisateur, calendrier et simulation complète de règle restent des cibles.
- `timeWindowMatches()` utilise l'uptime et son accès par le catalogue/validateur n'est pas garanti. Ne pas confondre avec la plage quotidienne NTP.
- Recopie/validation des règles dans un document temporaire à chaque cycle : optimisation proposée à la sauvegarde/reconfiguration, à mesurer.

### F — API et dashboard (P2)

Sources : `WebUi::{sendJson,saveConfig,sendStatusLite,litePage}`, `data/www/app.js::{pidState,energyFlowSvg,updateDashboardLiveSections}`.

`/lite` échoue toujours en syntaxe JS. Certains refus de sauvegarde en HTTP 200 peuvent effacer l'indicateur de modifications locales. Une réponse commande `202 queued` confirme la mise en file, pas l'exécution électrique.

Reproductions DOM simulé : réseau -200 W / consigne 0 W donne -200 W dans le secours de `pidState()`, contre +200 W dans le firmware ; réseau absent donne classe `neutral` et mention d'équilibre. `consumptionW` reste l'achat positif, présenté comme puissance « Maison ».

Le choix AUTO de la source PID API privilégie maintenant la TIC disponible : défaut de priorité JSY de l'audit dashboard **partiellement corrigé**. Identifiant exact et origine restent inférés par type/configuration, sans garantie avec plusieurs compteurs identiques.

Le rafraîchissement partiel remplace trois sections, pas tout le bandeau supérieur. Le polling runtime actionneurs à 1 s préserve maintenant les contrôles ; il ne valide pas les autres rafraîchissements. Commande affichée et puissance estimée ne prouvent pas une exécution distante ; ACK toujours `NOT_SUPPORTED`.
